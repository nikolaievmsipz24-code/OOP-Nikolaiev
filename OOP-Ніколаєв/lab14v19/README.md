## 2. Аналіз принципів SRP та OCP

### 2.1. Два приклади вдалого застосування SRP

#### Приклад 1: `OrderService` у репозиторії `eShopOnWeb`
* **Посилання на код:**  
  [`src/ApplicationCore/Services/OrderService.cs`](https://github.com/dotnet-architecture/eShopOnWeb/blob/main/src/ApplicationCore/Services/OrderService.cs) (рядки 15–56, метод `CreateOrderAsync`).
* **Де саме в коді видно принцип:**  
  Клас `OrderService` відповідає виключно за оркестрацію створення замовлення: він завантажує кошик через `IRepository<Basket>`, формує об'єкти `OrderItem` та `Order`, зберігає замовлення через `IRepository<Order>` і передає повідомлення в `IUriComposer`. Він не займається SQL-запитами, валідацією HTTP-запитів чи відправкою листів.
* **Переваги/ризики для підтримки:**  
  Перевагою є висока тестованість (усі залежності передаються через інтерфейси в конструктор) і зрозуміла зона відповідальності. Ризик мінімальний — лише необхідність підтримувати узгодженість між кількома невеликими сервісами.
* **Що зміниться при додаванні нової функції:**  
  Якщо зміниться спосіб збереження замовлення (наприклад, перехід з EF Core на інше сховище) або формат генерації посилань на зображення, `OrderService` змінювати не доведеться — зміняться лише відповідні реалізації репозиторію чи `IUriComposer`.

#### Приклад 2: `MessageTemplateParser` у репозиторії `Serilog`
* **Посилання на код:**  
  [`src/Serilog/Parsing/MessageTemplateParser.cs`](https://github.com/serilog/serilog/blob/dev/src/Serilog/Parsing/MessageTemplateParser.cs) (рядки 22–135, метод `Parse`).
* **Де саме в коді видно принцип:**  
  Єдина відповідальність класу — розбір рядка шаблону логування (наприклад, `"User {UserId} logged in"`) на послідовність токенів `TextToken` та `PropertyToken`. Клас нічого не знає про рівні логування, фільтрацію, форматування в JSON чи запис у файл/консоль.
* **Переваги/ризики для підтримки:**  
  Парсер ізольований від побічних ефектів вводу/виводу, тому його легко покривати модульними тестами та оптимізувати за швидкодією без ризику зламати вивід логів.
* **Що зміниться при додаванні нової функції:**  
  При додаванні нового способу виводу логів (наприклад, у хмарне сховище) парсер не зачіпається взагалі. Зміни в `MessageTemplateParser` потрібні лише тоді, коли змінюється сам синтаксис шаблонів повідомлень.

### 2.2. Два приклади порушення SRP

#### Приклад 1: `LoggerConfiguration` у репозиторії `Serilog`
* **Посилання на код:**  
  [`src/Serilog/LoggerConfiguration.cs`](https://github.com/serilog/serilog/blob/dev/src/Serilog/LoggerConfiguration.cs) (рядки 35–350, властивості `WriteTo`, `AuditTo`, `Enrich`, `Filter`, `Destructure`, `MinimumLevel` та метод `CreateLogger()`).
* **Де саме в коді видно порушення:**  
  Клас поєднує роль зручного Fluent-API білдера для користувача з логікою збирання всіх конвеєрів обробки, налаштування збагачувачів (enrichers), політик деструктуризації, фільтрів, рівнів логування та конструювання фінального екземпляра `Logger` (рядки 240–345).
* **Ризики/переваги для підтримки:**  
  Перевага — зручна єдина точка входу для розробника (`new LoggerConfiguration()...CreateLogger()`). Ризик — розростання класу («God-builder»): будь-яке нове налаштування ядра вимагає редагування цього ж файлу, що ускладнює навігацію та збільшує кількість причин для зміни класу.
* **Що зміниться при додаванні нової функції:**  
  Додавання нового типу конвеєра або глобального механізму перехоплення подій вимагатиме додавання нових полів, властивостей і логіки збірки безпосередньо в `LoggerConfiguration.CreateLogger()`.

#### Приклад 2: `CatalogController` (або `OrderController` / `BasketController` в API/Web) у репозиторії `eShopOnWeb`
* **Посилання на код:**  
  [`src/Web/Controllers/OrderController.cs`](https://github.com/dotnet-architecture/eShopOnWeb/blob/main/src/Web/Controllers/OrderController.cs) (рядки 17–58, методи `MyOrders` та `Detail`).
* **Де саме в коді видно порушення:**  
  Окрім обробки HTTP-маршрутизації та авторизації (`[Authorize]`), контролер бере на себе пряму взаємодію з шаром доступу до даних (`IMediator` для запитів), мапінг доменних сутностей у `OrderViewModel` (як-от ручне заповнення `OrderItems` у `Detail`, рядки 43–55) та перевірку належності замовлення поточному користувачеві.
* **Ризики/переваги для підтримки:**  
  Для невеликого демонстраційного проєкту це економить кількість файлів, але при масштабуванні контролер починає змінюватися і через зміни HTTP-контракту, і через зміни структури ViewModel або бізнес-правил доступу до деталей замовлення.
* **Що зміниться при додаванні нової функції:**  
  Якщо знадобиться додати нові поля в деталі замовлення або повторно використати логіку перевірки власника замовлення в REST API, її доведеться дублювати або виносити з `OrderController`.

### 2.3. Два приклади розширення за OCP

#### Приклад 1: `ILogEventSink` у репозиторії `Serilog`
* **Посилання на код:**  
  Інтерфейс [`src/Serilog/Core/ILogEventSink.cs`](https://github.com/serilog/serilog/blob/dev/src/Serilog/Core/ILogEventSink.cs) (рядки 22–31, метод `Emit(LogEvent logEvent)`) та його реалізації, наприклад [`src/Serilog/Core/Sinks/SafeAggregateSink.cs`](https://github.com/serilog/serilog/blob/dev/src/Serilog/Core/Sinks/SafeAggregateSink.cs).
* **Де саме в коді видно принцип:**  
  Ядро `Serilog` працює виключно з абстракцією `ILogEventSink`. Уся екосистема приймачів логів (`Serilog.Sinks.Console`, `Serilog.Sinks.File`, `Serilog.Sinks.Seq` тощо) реалізує один метод `Emit(LogEvent logEvent)` без модифікації вихідного коду ядра бібліотеки.
* **Переваги/ризики для підтримки:**  
  Максимальна розширюваність: сотні сторонніх пакетів підключаються як плагіни. Ризик — необхідність суворо дотримуватися зворотної сумісності самого контракту `ILogEventSink`.
* **Що зміниться при додаванні нової функції:**  
  Щоб додати запис логів у нове сховище (наприклад, Telegram або Elasticsearch), створюється новий клас із реалізацією `ILogEventSink`, а код ядра `Serilog` залишається незмінним.

#### Приклад 2: Патерн Specification (`ISpecification<T>`) у репозиторії `eShopOnWeb`
* **Посилання на код:**  
  Використання специфікацій у [`src/ApplicationCore/Specifications/CatalogFilterPaginatedSpecification.cs`](https://github.com/dotnet-architecture/eShopOnWeb/blob/main/src/ApplicationCore/Specifications/CatalogFilterPaginatedSpecification.cs) (рядки 8–20) та [`src/ApplicationCore/Specifications/CustomerOrdersWithItemsSpecification.cs`](https://github.com/dotnet-architecture/eShopOnWeb/blob/main/src/ApplicationCore/Specifications/CustomerOrdersWithItemsSpecification.cs).
* **Де саме в коді видно принцип:**  
  Замість того щоб додавати в `IRepository<T>` десятки нових методів під кожен фільтр (`GetByBrand`, `GetByTypeAndBrand`, `GetPaged...`), репозиторій залишається закритим для модифікації, а нові правила вибірки даних додаються через створення нових класів-специфікацій, успадкованих від `Specification<T>`.
* **Переваги/ризики для підтримки:**  
  Уникаємо розростання інтерфейсів репозиторіїв і дублювання LINQ-запитів. Ризик — для дуже складних нестандартних SQL-запитів специфікації можуть бути менш гнучкими, ніж спеціалізовані query-об'єкти.
* **Що зміниться при додаванні нової функції:**  
  При появі нового фільтра в каталозі (наприклад, фільтрації за діапазоном цін або наявністю знижки) достатньо додати новий клас специфікації без зміни коду `EfRepository<T>` чи `IRepository<T>`.

## 3. Пропозиція рефакторингу для найгіршого прикладу

**Обраний приклад:** `OrderController` у `eShopOnWeb` (`src/Web/Controllers/OrderController.cs`, метод `Detail`, рядки 36–57), де в одному методі контролера змішано перевірку прав доступу, отримання даних і ручний мапінг сутності `Order` у `OrderViewModel`.

### Поточна проблема (спрощено)
```csharp
[HttpGet("{orderId}")]
public async Task<IActionResult> Detail(int orderId)
{
    var viewModel = await _mediator.Send(new GetOrderDetails(User.Identity.Name, orderId));
    if (viewModel == null)
    {
        return BadRequest("No such order found for this user.");
    }
    return View(viewModel);
}
(Примітка: у різних версіях/контролерах проєкту логіка формування OrderViewModel та перевірки користувача часто осідає в контролері або змішує HTTP-статуси з бізнес-перевіркою).

Пропозиція рефакторингу
Розділити відповідальності на три окремі компоненти:

Запит і обробник (GetOrderDetailsQuery + GetOrderDetailsHandler) — відповідає лише за отримання замовлення за специфікацією та перевірку належності користувачу.

Мапер (OrderViewModelMapper або ToViewModel()) — окремий клас, відповідальний виключно за перетворення доменної моделі Order у OrderViewModel.

Контролер (OrderController) — працює лише як тонкий HTTP-адаптер: приймає orderId, викликає медіатор і повертає View(...) або NotFound()/Forbid().

C#
// 1. Окремий мапер 
public static class OrderViewModelMapper
{
    public static OrderViewModel Map(Order order) => new()
    {
        OrderNumber = order.Id,
        OrderDate = order.OrderDate,
        ShippingAddress = order.ShipToAddress,
        Total = order.Total(),
        OrderItems = order.OrderItems.Select(item => new OrderItemViewModel
        {
            ProductId = item.ItemOrdered.CatalogItemId,
            ProductName = item.ItemOrdered.ProductName,
            UnitPrice = item.UnitPrice,
            Units = item.Units
        }).ToList()
    };
}

// 2. Тонкий контролер 
[HttpGet("{orderId}")]
public async Task<IActionResult> Detail(int orderId)
{
    var orderDto = await _mediator.Send(new GetOrderDetailsQuery(User.Identity!.Name!, orderId));
    if (orderDto is null)
    {
        return NotFound();
    }

    return View(orderDto);
}
Обґрунтування: Такий рефакторинг ізолює правила мапінгу від ASP.NET Core інфраструктури, дозволяє тестувати формування OrderViewModel без створення HttpContext і дає змогу перевикористовувати запит GetOrderDetailsQuery у Web UI та Public API.

4. Висновки
Аналіз репозиторіїв eShopOnWeb та Serilog показав, що дотримання SRP та OCP безпосередньо визначає, наскільки дешево система масштабується з часом. У Serilog виділення парсера шаблонів (MessageTemplateParser) та контракту ILogEventSink дозволило створити величезну екосистему сторонніх sink-плагінів без зміни ядра бібліотеки. В eShopOnWeb поєднання сервісів рівня застосунку (OrderService) і патерну Specification дає змогу додавати нові критерії вибірки даних без модифікації репозиторіїв. Водночас навіть у якісних проєктах трапляються компроміси з SRP — наприклад, у класах конфігурації (LoggerConfiguration) або контролерах, де накопичується логіка підготовки моделей. Вчасне винесення мапінгу та бізнес-перевірок в окремі класи зберігає код чистим, тестованим і готовим до розширення.

5. Відповіді на контрольні запитання
1. Як відрізнити окрему відповідальність класу від просто великого обсягу коду?
За принципом SRP відповідальність визначається причиною для зміни (actor / reason to change), а не кількістю рядків коду. Клас може мати 300 рядків, але виконувати одну чітку задачу (наприклад, MessageTemplateParser, який лише розбирає синтаксис рядка). І навпаки, клас на 80 рядків порушує SRP, якщо одночасно валідує бізнес-правила, форматує JSON і зберігає дані в БД — адже зміна будь-якої з цих трьох вимог змусить редагувати той самий клас.

2. Які ознаки в коді найкраще підтверджують дотримання OCP?
Наявність стабільних абстракцій (interface, abstract class, делегати) у ключових точках розширення (як ILogEventSink чи ISpecification<T>).

Додавання нової поведінки відбувається шляхом створення нових класів і їх реєстрації через DI або конфігурацію, а не через дописування нових гілок if / else або switch в існуючому коді.

Основні оркеструючі класи залежать від абстракцій, а не від конкретних реалізацій.

3. Чому для аналізу SRP/OCP важливо дивитися не лише на інтерфейси, а й на місця розширення системи?
Сама наявність інтерфейсу ще не гарантує дотримання SOLID: інтерфейс може мати лише одну реалізацію або бути «товстим» (порушуючи ISP/SRP). Реальна якість архітектури проявляється в точках розширення — там, де в систему додають нову функціональність (новий тип оплати, новий фільтр каталогу, новий приймач логів). Якщо для цього доводиться змінювати центральний диспетчер, фабрику з великим switch або репозиторій, принцип OCP фактично не працює.

4. Які ризики виникають, якщо застосовувати рефакторинг «під патерн» без реальної потреби?
Надмірна складність (Over-engineering): замість одного зрозумілого класу з'являються десятки дрібних інтерфейсів, фабрик і адаптерів, через що стає важко відстежити потік виконання програми.

Сповільнення розробки: прості зміни вимагають редагування багатьох файлів і шаблонного коду (boilerplate).

Хибні абстракції: якщо точок варіативності ще немає, розроблений наперед інтерфейс може виявитися незручним для реальних майбутніх вимог, і його все одно доведеться переробляти.
