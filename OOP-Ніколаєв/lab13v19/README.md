# Звіт до лабораторної роботи №13 (Варіант 19)

**Тема:** Власні винятки та патерн Result.  
**Сценарій:** Обробка даних користувача (`InvalidUserDataException`, `Result<T>`, `UserProfileService`).

---

## Короткий висновок

У лабораторній роботі реалізовано власний виняток `InvalidUserDataException` (з властивостями `Field` та `Value`), узагальнений клас `Result<T>` із фабричними методами `Success` і `Failure`, а також сервіс `UserProfileService`. Для `UpdateProfile` доцільно використовувати `InvalidUserDataException`, оскільки порушення інваріантів моделі профілю свідчить про некоректний стан/виклик, який варто перервати та чітко локалізувати за полем і значенням. Для `ChangeEmail` краще підходить патерн `Result<bool>`, адже зайнятий email або некоректне введення користувача — це очікуваний бізнес-результат перевірки, який зручно обробити звичайним розгалуженням `IsSuccess`/`Error` без накладних витрат на винятки.

---

## Контрольні запитання та відповіді

### 1. Навіщо створювати власні типи винятків? Які переваги це дає?
Власні винятки дозволяють відображати специфічні предметні помилки застосунку (наприклад, `InvalidUserDataException`), а не обмежуватися загальними системними типами. Це дає:
* чітку семантику помилки в коді та логах;
* можливість додавати додаткові властивості з контекстом (`Field`, `Value`, коди помилок, ID сутностей);
* вибіркову обробку різних типів збоїв у різних блоках `catch`.

### 2. Які стандартні конструктори рекомендується реалізовувати для власних винятків?
Для класу, успадкованого від `Exception`, зазвичай реалізують три стандартні конструктори:
1. Конструктор без параметрів: `public InvalidUserDataException() { }`
2. Конструктор з повідомленням: `public InvalidUserDataException(string message) : base(message) { }`
3. Конструктор з повідомленням і внутрішнім винятком: `public InvalidUserDataException(string message, Exception innerException) : base(message, innerException) { }`

За потреби додають спеціалізовані конструктори з власними властивостями (як `Field` та `Value`).

### 3. Поясніть патерн Result. У яких випадках його використання є більш доцільним, ніж викидання винятків?
Патерн `Result<T>` повертає об'єкт-контейнер, який містить або успішне значення `Value` (`IsSuccess = true`), або опис помилки `Error` (`IsSuccess = false`). Його доцільніше використовувати тоді, коли «невдача» є передбачуваним, штатним результатом бізнес-логіки або перевірки вводу (наприклад, email уже зайнятий, користувача не знайдено, умова не виконана), щоб уникнути зайвого створення стектрейсів та не керувати стандартним потоком виконання через `try-catch`.

### 4. Які сценарії краще обробляти через винятки, а які через патерн Result?
* **Через винятки** краще обробляти виняткові ситуації, порушення контрактів/інваріантів та системні збої (невалідний стан об'єкта у `UpdateProfile`, відсутність обов'язкових залежностей, збої IO/мережі чи БД), де нормальне продовження операції неможливе.
* **Через патерн `Result<T>`** краще обробляти очікувані бізнес-відмови та перевірки умов (як-от зайнятий email у `ChangeEmail`, відмова у доступі за бізнес-правилом чи помилка парсингу/валідації форми), де викликаючий код повинен спокійно перевірити результат і показати користувачу зрозуміле повідомлення.
