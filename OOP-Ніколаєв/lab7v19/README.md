# Лабораторна робота №7: Узагальнені типи (Generics). IRepository з де-обмеженнями та тестами

## Опис структури проєкту

У даному проєкті реалізовано патерн "Репозиторій" з використанням узагальнених типів (Generics) для ізоляції логіки доступу до даних. Проєкт складається з наступних ключових компонентів:

*   **`IEntity`**: Базовий інтерфейс, який вимагає наявності властивості `int Id { get; set; }`. Використовується для гарантії того, що будь-яка сутність, яка передається в репозиторій, має унікальний ідентифікатор.
*   **Сутність `Event` (Варіант 19)**: Клас, що описує подію. Реалізує інтерфейс `IEntity` та містить властивості:
    *   `Id` (int) — унікальний ідентифікатор;
    *   `Name` (string) — назва події;
    *   `Location` (string) — місце проведення;
    *   `EventDate` (DateTime) — дата та час події.
*   **`IRepository<T>`**: Узагальнений інтерфейс для абстрагування логіки доступу до даних. Містить базові CRUD-операції (`Add`, `GetById`, `GetAll`, `Update`, `Delete`). На параметр `T` накладено обмеження `where T : IEntity`, що дозволяє інтерфейсу безпечно взаємодіяти з властивістю `Id` будь-якого переданого типу.
*   **`InMemoryRepository<T>`**: Узагальнена реалізація `IRepository<T>`. Використовує внутрішню колекцію `List<T>` для тимчасового зберігання даних у пам'яті (RAM) під час роботи програми. Ідеально підходить для розробки та юніт-тестування.

## Відповіді на контрольні запитання

### 1. Яка роль where-обмежень у Generics? Наведіть приклади їх використання.
Обмеження `where` вказують компілятору, які саме типи можуть бути передані як параметри (аргументи типу) до узагальненого класу чи методу. Без обмежень компілятор сприймає `T` як звичайний `object`, тому ми не маємо доступу до специфічних методів чи властивостей типу. 
**Приклади:**
*   `where T : IEntity` — тип має реалізовувати інтерфейс `IEntity` (це дозволило нам звертатися до `item.Id` всередині репозиторію).
*   `where T : class` — тип має бути посилальним (клас, інтерфейс, делегат).
*   `where T : struct` — тип має бути значущим (наприклад, `int`, `DateTime`).
*   `where T : new()` — тип повинен мати публічний конструктор без параметрів.

### 2. Навіщо потрібен шаблон IRepository? Які переваги він дає?
Шаблон *Repository* виступає посередником між бізнес-логікою програми (Domain) та шаром доступу до даних (Data Access). 
**Його переваги:**
*   **Абстракція:** Бізнес-логіка не знає, як саме зберігаються дані (в пам'яті, у базі даних SQL, у файлах тощо).
*   **Гнучкість:** Можна легко змінити базу даних або ORM (наприклад, перейти з `List<T>` на Entity Framework Core), просто створивши нову реалізацію `IRepository<T>`, не змінюючи основний код програми.
*   **Тестованість:** Завдяки інтерфейсу дуже легко створювати моки (mocks) та писати юніт-тести для бізнес-логіки.

### 3. Поясніть, чому юніт-тести є важливими при розробці узагальнених компонентів.
Узагальнені компоненти (Generics) пишуться один раз, але використовуються з багатьма різними типами даних по всій програмі. Якщо в логіці `InMemoryRepository<T>` буде помилка (наприклад, неправильно працює оновлення об'єкта або видалення), ця помилка зламає роботу *всіх* сутностей у проєкті, які використовують цей репозиторій. Юніт-тести гарантують, що загальна логіка працює коректно, ізольовано та стабільно, а також правильно обробляє крайні випадки (наприклад, пошук за неіснуючим ID).

### 4. Які проблеми вирішують Generics порівняно з використанням object?
*   **Типізація (Type Safety):** При використанні Generics помилки типів виявляються на етапі компіляції, а не під час виконання програми. Якщо спробувати покласти `string` у `List<int>`, код просто не скомпілюється. При використанні `object` помилка вилізе як `InvalidCastException` під час запуску програми.
*   **Продуктивність:** При використанні значущих типів (наприклад, `int`) з `object` відбувається процес пакування (boxing) і розпакування (unboxing), що вимагає додаткових ресурсів процесора та пам'яті. Generics працюють з типами напряму, уникаючи цих витрат.
*   **Читабельність коду:** Не потрібно постійно писати явні приведення типів (casting), як це було б при використанні `object`.
