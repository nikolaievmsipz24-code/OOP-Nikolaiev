**Виконавець:** Ніколаєв Максим

## 1. Опис реалізації

У проєкті `InvertedIndexDemo` реалізовано:
* **`Document`** — модель документа (`Id`, `Title`, `Content`).
* **`TextProcessor`** — токенізація тексту з приведенням до нижнього регістру та видаленням пунктуації (`Tokenize`), а також фільтрація стоп-слів (`RemoveStopWords`).
* **`InvertedIndex`** — інвертований індекс на базі `Dictionary<string, HashSet<int>>` (`_index`) та словника документів `Dictionary<int, Document>` (`_documents`) з методами:
  * `AddDocument(Document doc)` — індексує слова документа та додає `doc.Id` у `HashSet<int>` відповідного слова;
  * `SearchSingleWord(string word)` — знаходить документи за одним словом;
  * `SearchMultipleWords(params string[] words)` — обчислює перетин множин документів (`IntersectWith`) для запиту логічного **І (AND)**;
  * `SearchAnyWord(params string[] words)` — об'єднує множини документів (`UnionWith`) для запиту логічного **АБО (OR)**.
* **`PerformanceTest`** — порівняння лінійного пошуку (`Where` + `Tokenize` по кожному документу) та пошуку через `InvertedIndex` з однаковими правилами нормалізації тексту.

## 3. Висновки

Інвертований індекс перетворює повнотекстовий пошук із повного перебору всіх документів на миттєве звернення до списку ID документів за ключовим словом. Поріг вигідності індексу залежить від співвідношення **кількості запитів** і **кількості документів**: для одноразового пошуку в 10 документах будувати індекс зайве, але коли документів сотні чи тисячі і пошукових запитів багато, індекс швидко окупається та працює на порядки швидше за лінійний пошук. Водночас індекс потребує додаткової оперативної пам'яті та часу на його побудову/оновлення при зміні документів.

## 4. Контрольні запитання та відповіді

### 1. Чому структура `Dictionary<string, HashSet<int>>` добре підходить для реалізації інвертованого індексу?
`Dictionary<string, HashSet<int>>` дозволяє швидко знаходити множину ID документів за словом у середньому за $O(1)$, а `HashSet<int>` автоматично виключає дублювання ідентифікаторів документів (навіть якщо слово зустрічається в одному документі кілька разів) і підтримує ефективні множинні операції.

### 2. Які переваги `HashSet<T>` дає під час обчислення AND/OR-пошуку за кількома словами?
Для логічного **AND** метод `IntersectWith` знаходить спільні ID документів одразу для всіх слів без ручних вкладених циклів і зайвих копій, а для логічного **OR** метод `UnionWith` об'єднує множини документів, автоматично відкидаючи повтори.

### 3. Чому під час вимірювання продуктивності важливо однаково нормалізувати текст для лінійного пошуку та пошуку через індекс?
Якщо лінійний пошук і індекс по-різному оброблятимуть регістр, пунктуацію чи символи на кшталт `c#`, вони повертатимуть різну кількість знайдених документів і виконуватимуть неоднаковий обсяг роботи. Однакова нормалізація гарантує, що ми порівнюємо саме алгоритми пошуку на однакових даних.

### 4. Які обмеження має проста реалізація інвертованого індексу без ранжування, стемінгу та підтримки фраз?
Без ранжування (наприклад, TF-IDF або підрахунку частоти слова) результати не сортуються за релевантністю. Без стемінгу/лематизації слова з різними закінченнями (`programming`, `programs`) вважаються різними токенами, а без збереження позицій слів неможливо точно знайти сусідні слова у фразі (`"c# programming"`).
